# Changelog

Заметные изменения Conductor. Формат свободный, даты — ISO.

## Unreleased — 2026-11-04 (после v2.2.0)

- Пределы времени автоматических проверок стали настраиваемыми. Повод: на Windows-машине
  GitHub проверка синтаксиса JavaScript один раз промолчала о сломанном файле — первый
  запуск `node` занял больше 5 секунд, а по истечении предела проверка по замыслу молчит;
  тест прочитал это как «ошибка не замечена». Причина воспроизведена подставной медленной
  программой. Теперь: `CONDUCTOR_SYNTAX_CHECK_SECONDS` (1–60, по умолчанию 5) для проверки
  файлов shell и JavaScript после правки, `CONDUCTOR_RECALL_SECONDS` и
  `CONDUCTOR_PLAN_STATUS_SECONDS` (1–10, по умолчанию 3) для подбора уроков и строки
  состояния плана; непригодное значение = предел по умолчанию. Тесты выставляют наибольший
  предел, а поведение при его превышении проверяется отдельно подставной медленной
  программой. Ограничитель времени в `user-prompt.sh` теперь выбирается так же строго, как
  в `lessons-inject.sh`: `/usr/bin/timeout` или программа, которая сама называет себя GNU —
  на Windows поиск по PATH мог найти одноимённую системную `timeout.exe`, с которой и
  подбор уроков, и строка плана молча не работали бы. Таблица переменных — в трёх README.

- Состояние плана читается из git, а не ведётся руками. Карта `.conductor/work-map.md`
  теперь хранит только план (ветка сборки, число тяжёлых полос, строки `decided:`, таблица
  шагов `id | step | area | needs | proof | weight`); столбцов «кто» и «состояние» в ней
  больше нет. Новая программа `runtime/evidence/plan.py` (разбор карты — `plan_map.py`,
  чтение фактов — `plan_state.py`): `status` показывает по каждому шагу «идёт / сдан /
  принят / возвращён N раз», списки «можно начинать» и «к приёмке» и называет расхождения
  (файл вне области шага, ветка сдвинулась после сдачи, шаг начат на непринятой основе,
  слияние без сдачи, области двух неупорядоченных шагов пересекаются, записи и ветки, которых
  нет в карте); `start` занимает шаг (из двух сессий удаётся ровно одной — вместо каталога-
  заявки; отказывает, если область пересекается с идущим шагом), `handin` записывает сдачу
  после проверки области, `accept` сам вливает сданный коммит в ветку сборки и записывает
  приёмку (отказывает, если основа шага не принята, ветка сдвинулась после сдачи или
  слияние не проходит чисто — тогда незавершённое слияние отменяется), `return` считает
  раунды возврата, `rebased` — новая основа после перебазирования (сдача отзывается без
  счёта раунда), `release` освобождает начатый шаг, `finish` печатает решения, убирает
  записи и удаляет файл карты. Записи лежат в `refs/conductor/` — это не ветки и не теги,
  `git push` их не отправляет. «Принят» = приёмку выполнила команда `accept`; как потом
  выглядит история ветки сборки, не важно. Область шага проверяется вопросом «что это
  слияние изменит в ветке сборки»: при сдаче — по разнице с точкой, где ветки сошлись, при
  приёмке — по самому слиянию до его фиксации; файл из третьей ветки и откат чужой принятой
  работы считаются наравне с прямой правкой. Всё, что попало в ветку сборки мимо `accept`
  (слияние руками, прямой коммит, влитая ветка владельца), называется, пока его не
  посмотрят и не выполнят `acknowledge`. Приёмки идут по одной: вторая, запущенная в то же
  мгновение, отказывает и просит повторить, ничего не трогая. Первые версии выводили приёмку и область из формы
  истории git — круги независимой проверки показали, что обычное слияние могло
  «разпринять» шаг, а проверку области можно было обойти, и подход был заменён.
  К каждому сообщению пользователя, пока файл карты
  существует, добавляется одна строка состояния (`user-prompt.sh`, предел 3 с, при ошибке
  строки нет; текст находок в неё не попадает — в нём бывают имена файлов, выбранные
  исполнителем); выключатель `CONDUCTOR_PLAN_STATUS=0`. `scheduling.md` переписан под
  команды, предел 8800 → 10200; каталог заявок остался только для тяжёлых полос. Проверки:
  `qa/plan-test.py` на настоящих репозиториях (в CI на Linux и Windows); каждая защита
  отключалась по одной, и проверки это замечали. Независимый проверяющий проходил правила
  буквально на четырёх ситуациях в несколько кругов; найденное исправлено и закрыто
  проверками. Пределы: программа не мешает слить руками мимо правил — она это называет при
  следующем `status`; учитываются только коммиты, несохранённые правки не видны; ветке
  сборки нужна своя рабочая копия (в ней выполняется слияние приёмки); условия раннего старта «только через контракт» и «нет
  общего живого ресурса» остаются на суждении агента; кто ведёт шаг и что он заблокирован,
  записывается строкой в карте; одиночный режим по-прежнему ведёт состояния в записи о
  задаче.

- Работа по плану без простоев: новый плейбук `runtime/playbooks/scheduling.md`, подключается
  при плане из 3+ доказуемых шагов или 2+, которые могут идти одновременно. Два режима.
  ОДИНОЧНЫЙ (один агент, одна копия, никто больше не пишет): без файла карты, меток, веток и
  коммитов без просьбы; список шагов (область записи, зависимости, узкая проверка, вес,
  состояние) живёт в записи о задаче; пока идёт проверка, агент только читает и готовит
  следующий шаг. КОМАНДНЫЙ (пишут исполнители или другие сессии): карта
  `.conductor/work-map.md` в главной копии, новая временная ветка сборки плана в своей
  рабочей копии (никогда не рабочая ветка пользователя), каждый шаг в своей копии, сдача
  одним коммитом, скептик на сдачу исполнителя сразу и параллельно, ведущий сам смотрит diff и
  вывод проверки и решает; после последнего шага владельца спрашивают один раз — влить или
  оставить ветку (T3 — через Integration с одобрением); карта удаляется после ответа и
  отчёта с решениями, принятыми без владельца. Общее для обоих режимов: лестница ожидания
  (нельзя закончить ход словом «жду», пока есть готовый шаг, сдача к приёмке или подготовка
  следующего шага), ранний старт зависимого шага на глубину 1, счёт тяжёлых проверок по
  наблюдению за памятью (начинается с одной; сборка на все ядра — всегда одна).
  `orchestration.md`: приёмка больше не объявлена последовательной, скептик — один на
  проверяемый результат. `skeptic.md`: сданный коммит в своей копии — неподвижное дерево.
  Ядро: тот же смысл короче в пяти местах (ни один запрет не снят — сверено независимым
  проверяющим построчно) и строка о новом плейбуке в списке модулей; payload 9470/9500 на
  Linux и на 15 байт больше на Windows (там длиннее подставляемый путь): первый прогон CI
  на ветке поймал 9502/9500 на Windows при зелёном Linux.
  Проверено пятью раундами двух независимых проверяющих (сверка между файлами и буквальный
  проход четырёх ситуаций); после пятого обязательных правок не осталось. Первая версия
  была отвергнута третьим раундом целиком: одиночке она навязывала служебные файлы без
  пользы, а в команде вливала шаги в рабочую ветку до одобрения.
  (Позже в тот же день заявки на шаги и ручное ведение состояния заменены программой
  `plan.py` — см. запись выше; каталоги-заявки остались только для тяжёлых полос.)
  Известные пределы: метки-заявки — каталоги без срока годности; команды замера памяти для
  macOS и Windows и `cmd /c mkdir` на этих системах не запускались; равные сессии на разных
  машинах заявок друг друга не видят; в дайджесты Cursor и Antigravity правила не вошли.
- «Сначала красное» вместо тройного прогона: тест пишется до исправления и обязан упасть на
  неисправленном коде, после исправления — пройти (`debugging.md` шаг 6, `implementing.md`,
  `adapters/core-body.md`). Откат через `evidence/falsify.py` остаётся для теста,
  написанного после исправления. Требование «увидеть тест красным без исправления» не
  ослаблено, прогонов стало два вместо трёх. Решение владельца от 2026-11-11.
  Действует, только если два прогона отличаются одним исправлением (тот же тест, база и
  окружение) и падает собственное утверждение теста; тест, прошедший на неисправленном
  коде, чинится. После коммита `falsify.py` получает `--base <sha до исправления>`.
  Пределы: `implementing.md` 7500 → 7700, новый `scheduling.md` ≤8800.
  Эффект обоих изменений на поведение не измерен: мерить на живом плане.
- Сначала автоматическая проверка, потом просьба к человеку. За одну работу владельца шесть
  раз просили руками запускать установщик на Windows, хотя CI на Windows был доступен: он
  запускался только для `main` и для заявок на слияние, а заявки без просьбы владельца не
  открываются. CI теперь запускается для любой отправленной ветки (заявка из ветки этого же
  репозитория второй раз не проверяется, заявка из форка — проверяется; новая отправка в
  рабочую ветку отменяет устаревший прогон, прогоны `main` не отменяются). В `debugging.md` и
  `implementing.md` — правило: есть автоматический прогон на целевой платформе — использовать
  его до ручной проверки человеком. Предел `implementing.md` 7300 → 7500 (правила не
  сокращались). Эффект правила на поведение не измерен.
- Superpowers не ставился на компьютере без локальных плагинов, если аккаунт синхронизирует
  плагины с claude.ai: «superpowers: FAIL unrecognized plugin list». Причин две, обе
  необходимы: заголовок раздела бывает и в виде «Synced from claude.ai:» (разбор ждал пробел
  после `claude.ai`), а список из одного этого раздела — без «Installed plugins:» — не
  считался известной формой. Теперь это «локально ничего не установлено». Воспроизведено на
  настоящем `claude plugin list` (22 синхронизированных плагина, локальных нет); два новых
  теста в `qa/companions-test.py` падают на прежнем коде. Третья причина найдена на машине
  пользователя: под Git Bash в Windows Claude Code ставит перед записью не `>`, а
  многобайтовую стрелку (в окне PowerShell — `>`), и разбор не узнавал ни одной записи.
  Маркер записи теперь любой небуквенный знак, как уже было со значком статуса; `awk`
  работает в `LC_ALL=C`, чтобы байты значков не считались буквами в однобайтовой кодировке.
  Отказ теперь называет причину и первую непонятую строку — по ней причина и найдена.
- `install.ps1` показывал красное «Conductor bootstrap failed (exit 3)», когда Conductor
  установлен и проверен, а не поставился только сопутствующий инструмент. Код 3 теперь даёт
  предупреждение с объяснением, а не ошибку (тест только для Windows, не запускался).
- Установка после переноса папки `~/.claude` копированием падала с «locally modified or
  missing managed file: antigravity»: `install-state.json` переезжал вместе с папкой, а файлы,
  которые он перечисляет вне её (`~/.gemini/AGENTS.md`, `~/.codex/AGENTS.md`, команда
  `conductor`), — нет. Явная установка теперь ставит отсутствующие файлы заново (ничего
  существующего не перезаписывая); отсутствующий `settings.json` тоже не мешает.
  `conductor update` по-прежнему останавливается, но называет путь и говорит запустить
  установщик. Удаление больше не останавливается на файле, которого уже нет.
- Изменённый управляемый файл останавливал и установку, и удаление без выхода. Решение
  владельца: отказ по умолчанию, но с полным путём и готовой командой; `--replace-modified`
  (`install.ps1 -ReplaceModified`) сохраняет версию пользователя копией в папке резервной
  копии (`…/updates/<id>/replaced/`) и ставит текущий файл. Изменённый личный `CLAUDE.md` не
  заменяется никогда: с `--skip-global-md` или `--replace-modified` он остаётся как есть и
  выходит из записи установки (`keep_values` в `install-state.json`), после чего ни
  установка, ни обновление его не трогают и не останавливаются из-за него; раньше
  `--skip-global-md` при изменённом файле не помогал. Проверки: восемь новых тестов в
  `qa/bootstrap/test_unified.py`, все восемь падают на прежнем коде (`falsify.py`: PROVEN).
  Перенос на компьютер с ДРУГИМ путём профиля: хуки в скопированном `settings.json`
  указывают на старую папку, и установка останавливалась на их проверке с сообщением на
  пол-экрана. Теперь явная установка распознаёт перенос — регистрации целы и все ведут в одну
  прежнюю папку (`relocated()` в `tools/settings-json.py`) — и регистрирует их заново;
  изменённый вручную хук, вторая папка или пропавшая запись по-прежнему останавливают.
  `conductor update` этого не делает. Три новых теста в `qa/bootstrap/test_unified.py`.
- Установка на Windows падала с «Conductor requires Python 3.10+ on PATH» при установленном
  Python: когда в PATH есть и настоящий `python.exe`, и одноимённый ярлык Microsoft Store,
  `Get-Command` возвращает оба пути, а `install.ps1` запускал их как одно имя программы
  (сообщение пользователя: «Термин "…\Python314\python.exe …\WindowsApps\python.exe" не
  распознается»). Теперь каждое совпадение проверяется отдельно, добавлен кандидат `py`.
  Если Python не найден вовсе, установщик спрашивает согласие и только после `y` ставит
  через `winget` официальный менеджер установки Python и последнюю стабильную версию; без
  согласия, терминала или `winget` ничего не ставится. Проверки — `qa/bootstrap/test_launchers.py`
  (только Windows, оба PowerShell); в сессии автора PowerShell не было, поэтому доказательство —
  прогон CI на Windows, а установка через настоящий `winget` не прогонялась нигде.
- Облачные сессии Claude Code получали Conductor недельной давности: облако выполняет скрипт
  настройки один раз и переиспользует сохранённый результат (журнал запуска: «Skipping
  initialization script for faster startup»). Новая облачная сессия теперь сама обновляет
  Conductor до чтения ядра: `runtime/hooks/cloud-update.sh`, вызывается из уже
  зарегистрированного `session-start.sh` (своя регистрация сломала бы обновление старых
  установок). Только при `CLAUDE_CODE_REMOTE=true` и `source: startup`; через 5 с обновление
  получает SIGINT (и откатывает записанное), ещё через 2 с — SIGKILL; сбой не мешает старту;
  журнал — `cloud-update.log`; выключатель — `CONDUCTOR_AUTO_UPDATE=0`. Предел отсчитывает сам
  bash, без программы `timeout`: первый прогон CI показал, что `timeout` из uutils coreutils
  0.10.0 (образ ubuntu-latest) на `-s INT -k 2` убивает процесс сразу, без SIGINT, и
  обновление оборвалось бы посередине. Задание запускается с управлением заданиями (`set -m`):
  иначе bash стартует фоновую команду с игнорируемым SIGINT. Проверки:
  `qa/cloud-update-test.py` (12 тестов, включая «Python получает KeyboardInterrupt» и
  «не реагирующее на SIGINT обновление убивается»; защиты доказаны снятием) и живой прогон в
  песочнице: хук перевёл установку на текущий `main`. Прерывание настоящего обновления
  посередине не прогонялось.
- Решение владельца: Conductor пользуются несколько человек — установщики и обновления
  обязаны работать на чужих машинах, спрашивать согласие перед установкой сторонних программ,
  а новое автоматическое поведение — иметь документированный выключатель.
- README (RU/EN/AZ): что делать на macOS, если `conductor update` пишет «linked destination is
  not allowed». Установки старше 4 ноября не раскрывали путь временной папки macOS
  (`/var` → `/private/var`) и не могут обновиться сами; однократный запуск с настоящим путём
  (`TMPDIR="$(cd "${TMPDIR:-/tmp}" && pwd -P)" conductor update`) ставит новый код, где это уже
  исправлено. Воспроизведено со старым кодом, обход проверен на нём же.
- Ритуал нехолостости — одной командой: `conductor/evidence/falsify.py --test "<команда>" <файлы
  исправления>`. В отдельной копии текущего дерева (временный git worktree плюс все
  незакоммиченные изменения) файлы исправления возвращаются к снимку до правки (иначе к HEAD):
  тест обязан упасть; затем исправление возвращается со сверкой sha256, и тест обязан пройти.
  Настоящее дерево не пишется никогда, даже при обрыве. Тестовые файлы не трогаются.
  Подменённым файлам даётся новое время изменения, а Python запрещён кэш: иначе кэш
  сборки (pyc, cargo, make) при исправлении той же длины в ту же секунду подсовывал старую
  версию — это поймала первая же проверка. `debugging.md` шаг 6 и `implementing.md` теперь
  указывают на команду (ручной путь — только когда исправление и тест в одном файле, как в
  Rust). Наблюдение Rust-сессии проекта Basalt.
- Правила оркестрации: агент «только чтение» сдаёт отчёт последним сообщением, а не файлом;
  при вливании сначала основа вливается в ветку и проверяется это дерево, после вливания
  `git diff --quiet HEAD <ветка>` доказывает равенство деревьев — повторный прогон не нужен.
  Предел `orchestration.md` 7000 → 7400.
