# Параллельная работа исполнителей

**Как вести несколько задач одновременно, не превращая это в гонку правок.**

Документ написан по итогам практики на другом проекте (платформа Basalt) и предназначен
для внедрения в Conductor. Парный документ — `PROOF-LOOP.md` (контур доказательства);
здесь описано, что меняется в нём, когда исполнителей становится больше одного.

---

## 1. Зачем

Главный тормоз многослойной работы — не качество проверок, а **последовательность**. Пока
один слой идёт по циклу «написали → скептик → личный прогон владельца», следующий никто
не пишет. Цикл занимает часы, и большая их часть — ожидание.

Измерение с реального дня: слой проходил цикл около пяти часов, из которых написание кода
занимало меньше трети. Остальное — прогоны, разбор находок, повторные проверки. Всё это
время вторая независимая задача могла идти рядом и не шла.

Вывод простой: **параллелизм — норма, а не исключение.** Последовательное ведение при
непересекающихся областях — потеря темпа, а не осторожность.

---

## 2. Что можно вести параллельно

| Тип работы | Параллельно | Почему |
|---|---|---|
| Разведка кода (только чтение) | **да, веером** | ничего не меняет; несколько чтений разных подсистем безопасны всегда |
| Слои с непересекающимися файлами | **да** | ключевой случай, ради которого всё затевается |
| Инфраструктурная задача (конфигурация сборки, скрипты) | **да** | обычно живёт в собственных файлах |
| Слой + доработка другого слоя | **да, с оговорками** | см. §4, ловушка общих гейтов |
| Скептик + правки того же кода | **нет** | скептик сверяет контрольные суммы; движущееся дерево делает его вердикт бессмысленным |
| Две задачи в одних файлах | **нет** | последняя запись затирает предыдущую молча |
| Зависимые этапы (один нуждается в результате другого) | **нет** | второй будет доказывать на несуществующем основании |
| Финальная интеграция | **нет** | она и есть точка сборки; параллельность здесь бессмысленна |

## 3. Разведение областей — обязательный шаг

Перед запуском второго исполнителя владелец **явно перечисляет в каждом задании**:

1. **свою область** — списком файлов и каталогов;
2. **чужую область** — списком, с прямым запретом «эти файлы не трогай вообще»;
3. **что делать при пересечении** — остановиться и сообщить, а не редактировать общий
   файл «аккуратно».

Формулировка, которая работает: *«Параллельно с тобой другой исполнитель делает
такую-то работу; он работает в таких-то файлах; если твоя задача потребует общего файла —
остановись и верни отказ по границам, не редактируй его.»*

Без этого абзаца оба исполнителя действуют так, будто дерево принадлежит им одним.

## 4. Пять ловушек

### Ловушка 1. Гейты, требующие целого дерева

Самая дорогая и самая неочевидная. Проверки вида «собери весь проект», «прогони полную
матрицу конфигураций», «сравни режимы целиком» опираются на состояние **всего** дерева.
При параллельной работе один исполнитель неизбежно ломает дерево для другого — не
дефектом, а промежуточным состоянием своей работы.

Реальный случай: исполнитель закрыл все четыре находки скептика, прогнал свои проверки,
и был вынужден вернуть отказ — потому что общая проверка всего проекта падала на
незавершённом файле соседа. Ошибка была не его, а владельца, который поставил такой гейт
в оба параллельных задания.

**Решение:** гейты целого дерева **изымаются из параллельных заданий** и снимаются
владельцем лично после сериализации — когда все параллельные задачи завершены. В задании
остаются только точечные проверки своих модулей.

### Ловушка 2. Общий кэш сборки

Сборочные системы блокируют общий каталог артефактов. Два параллельных исполнителя не
ломают друг друга, но **ждут** в очереди, и выигрыш от параллельности частично съедается.

Это терпимо и обычно не требует действий. Но если задачи тяжёлые по сборке, стоит
понимать: параллельность даёт выигрыш на ожидании проверок и разборе находок, а не на
самой компиляции.

### Ловушка 3. Общие внешние ресурсы

Контейнеры, базы, порты, временные каталоги. Два исполнителя, поднимающие «базу для
теста» с одинаковым именем, получают конфликт или, хуже, тихо работают с чужими данными.

**Решение:** каждая задача обязана создавать ресурсы в **собственном пространстве имён**
с уникальным идентификатором, помечать их своим владельцем и удалять за собой в
завершающем блоке, доказывая нулевые счётчики. Чужие ресурсы не трогаются никогда — даже
если кажутся мусором.

Практика показала: при таком правиле параллельные живые тесты сосуществуют спокойно.
Владелец видит чужой контейнер, узнаёт по имени пространство соседа и не вмешивается.

### Ловушка 4. Доказательства становятся нестабильными

При параллельной работе фраза «весь проект зелёный» перестаёт быть доказательством
отдельной задачи: дерево менялось под ней, и зелёный цвет мог быть получен до или после
чужой правки.

**Решение:** каждый исполнитель доказывает **точечными прогонами своих модулей** и
обязан назвать в отчёте, что именно проверял. Владелец снимает общую картину сам, после
сериализации, и только она идёт в решение о приёмке.

### Ловушка 5. Непредупреждённый первый

Решение вести работу параллельно обычно приходит **после** запуска первой задачи. Первый
исполнитель работает по заданию, написанному для одиночного режима: с гейтами целого
дерева и без слова о соседе.

**Решение:** запуск второго исполнителя есть повод **дослать правку первому** — прямо в
его текущую работу: чем занят сосед, какие файлы теперь чужие, какие гейты снимаются.
Молча надеяться, что не столкнутся, — тот же класс ошибки, что и молчаливое допущение в
коде.

---

## 5. Протокол запуска

Перед запуском параллельной задачи владелец проходит короткий список:

1. **Пересекаются ли файловые области?** Если да — не параллелить или сузить задания.
2. **Пересекаются ли модели отказа?** Две задачи, ломающиеся по одной причине, дадут
   неразличимые симптомы — разделять бессмысленно.
3. **Есть ли в заданиях гейты целого дерева?** Изъять из обоих, оставить себе.
4. **Названы ли внешние ресурсы?** Уникальные пространства имён и уборка за собой.
5. **Предупреждён ли уже запущенный?** Дослать правку.
6. **Хватит ли меня на приёмку?** Каждая параллельная задача вернётся отчётом, который
   надо разобрать, проверить и принять. Это работа владельца, и она не параллелится.

---

## 6. Приёмка при параллельной работе

Порядок, который работает:

1. Все параллельные задачи завершаются и возвращают отчёты.
2. Владелец **сериализует**: дальше дерево не меняется.
3. Владелец снимает общие гейты — сборка целого проекта, матрица конфигураций, сквозные
   сравнения — один раз, за все задачи сразу.
4. Скептики запускаются **после** этого, по одному на задачу, на неподвижном дереве.
5. Приёмка выносится по каждой задаче отдельно, но на общем доказанном состоянии.

Обратный порядок — скептик по первой задаче, пока вторая ещё пишет, — даёт бесполезный
вердикт: скептик сверяет контрольные суммы файлов, а они меняются под ним.

---

## 7. Контроль границ — доверять, но сверять механически

Правило «чужого не трогай» держится на честном слове, пока его не проверяют. Проверка
дешёвая и обязана быть частью приёмки.

**Перед разбором отчёта** владелец сверяет фактически изменённое с объявленной областью:
список изменённых файлов минус область задачи должен быть пуст. Любой файл вне области —
находка, даже если правка выглядит безобидной: она могла затереть работу соседа, которую
тот ещё не показал.

**Что считать нарушением, а что нет.** Затронутый общий файл — нарушение. Созданный файл
в чужом каталоге — нарушение. А вот *переформатирование* чужого файла инструментом
(автоформатирование по всему проекту) — распространённый случайный вид нарушения, который
особенно легко пропустить: содержимое кажется тем же, но соседский рабочий файл переписан.
Поэтому в задании стоит прямо запрещать общие переформатирующие команды при параллельной
работе.

**Признак, который стоит проверять отдельно:** исполнитель, объявивший отказ по границам,
не должен был при этом ничего в чужой области изменить. «Я остановился, но заодно поправил
мелочь» — то же нарушение.

## 8. Порядок и состав

**Длинные первыми.** Если запустить короткую задачу раньше длинной, короткая закончится и
будет ждать сериализации. Обратный порядок даёт больший перехлёст.

**Не ставить рядом два новых слоя.** Их приёмки придут одновременно и упрутся в владельца,
который не параллелится. Удачные пары: новый слой + закрытие долга; новый слой +
инфраструктурная задача; доработка после скептика + независимый долг.

**Разведка — всегда первой и веером.** Она дешёвая, безопасная и даёт основание для
остальных решений. Пока читают код, можно готовить задания.

**Стоимость входа умножается.** Каждый параллельный исполнитель читает проект заново.
Три исполнителя — тройная цена чтения. Отсюда прямая связь с контуром доказательства:
свёрнутое состояние проекта (короткий документ вместо полных журналов) окупается тем
сильнее, чем больше исполнителей идут одновременно.

## 9. Ресурсные пределы машины

Параллельные сборки конкурируют не только за блокировку кэша, но и за память с
процессором. На слабой машине два исполнителя, каждый из которых компилирует крупный
проект, работают **медленнее**, чем один: система уходит в своп, сборки вытесняют друг
друга.

Практический ориентир: параллелить столько задач, сколько машина тянет **по памяти в пике
сборки**, а не по числу ядер. Если пик неизвестен — начинать с двух и смотреть.

Отдельно: живые тесты поднимают базы и контейнеры, и это тоже память. Две задачи, каждая
со своей базой, — норма; пять параллельных живых прогонов на обычной рабочей машине —
нет.

## 10. Пределы

**Сколько задач вести одновременно** определяется не желанием, а двумя вещами:
числом действительно независимых областей и способностью владельца принимать результаты.
Практика: две-три задачи идут спокойно; больше — владелец становится узким местом и
задачи начинают ждать уже его, а не друг друга.

**Когда остановиться:**
- если разведение областей требует искусственного дробления задачи — это признак, что
  области на самом деле одна;
- если приходится согласовывать промежуточные состояния между исполнителями — задачи
  зависимы, параллельность вредна;
- если владелец не успевает разбирать отчёты — очередь просто переехала, выигрыша нет.

## 11. Что параллелится всегда и без риска

**Разведка кода.** Несколько читающих агентов по разным подсистемам — самый выгодный
случай: они ничего не меняют, работают долго и возвращают карты, по которым принимаются
решения. Их можно пускать веером с первой минуты задачи.

Практика: три разведчика одновременно — по крейту, по способу подключения и по модели
данных — сократили подготовку слоя с часов до сорока минут, и ни один не помешал другому.

## 12. Как встроить в Conductor

Механизм ложится на существующую структуру, не переделывая её.

**В ядро (читается всегда):**
- параллелизм независимых задач — норма, а не исключение; последовательность при
  непересекающихся областях есть потеря темпа;
- гейты, требующие целого дерева, изымаются из параллельных заданий и снимаются
  владельцем после сериализации;
- при параллельной работе общий прогон перестаёт быть доказательством отдельной задачи.

**В плейбук оркестрации:**
- таблица «что можно вести параллельно» (§2);
- протокол запуска (§5) как список перед вторым исполнителем;
- порядок и состав (§8): длинные первыми, не два новых слоя рядом, разведка веером;
- ресурсные пределы (§9): считать по памяти в пике сборки, а не по ядрам.

**В плейбук скептика:**
- скептик запускается только на неподвижном дереве; при активных параллельных задачах
  его вердикт недействителен, потому что сверка контрольных сумм теряет смысл.

**В контракт субагента:**
- своя область списком, чужая — списком с прямым запретом;
- пересечение = остановка с отказом по границам, а не аккуратная правка общего файла;
- запрет общих переформатирующих команд при параллельной работе;
- внешние ресурсы — в собственном пространстве имён, уборка за собой с доказанными нулями,
  чужие ресурсы не трогаются никогда;
- в отчёте называть, какие модули реально проверял.

**В приёмку:**
- сверка изменённого с объявленной областью (§7) до разбора отчёта;
- общие гейты — один раз, за все задачи сразу, после сериализации.

**Чего не делать:**
- не параллелить ради параллельности: две задачи, которые придётся согласовывать между
  собой, дешевле сделать по очереди;
- не запускать скептика «пока другой доделывает» — вердикт придётся выбросить;
- не считать параллельность заменой узким заданиям: широкая задача, запущенная дважды,
  срывается дважды.

---

## 13. Одна фраза, если запомнить только её

> Параллелить можно всё, что не делит файлы, ресурсы и доказательства.
> Всё, что делит хоть одно из трёх, — сериализуется, и сериализует это владелец, а не
> случай.
