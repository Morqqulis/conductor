## Согласованная задача — реализация проверена 26 сентября

Общая для агентов и сессий **одного проекта** память о выполненных проверках.
Механизм устанавливается глобально вместе с Conductor, но данные строго разделяются
по проектам и привязаны к проверенному содержимому и условиям запуска.
Успех в проекте А ничего не доказывает для проекта Б. Разные рабочие копии и
незакоммиченные изменения тоже нельзя считать одинаковым состоянием по одному имени проекта.

Это развитие существующего правила повторного использования доказательств из
[verification.md](../runtime/playbooks/verification.md), а не новый запрет или обязательный
повтор всех тестов. Нынешний журнал активности прямо не является достаточным доказательством
для повторного использования; его записи не следует автоматически повышать до такого статуса.

Обсуждённый пример: Claude проверил модуль; позже Codex может прочитать команду, полный
результат и сведения о проверенном содержимом. Повторный запуск можно пропустить только
при установленной применимости. Неизвестные или изменившиеся значимые входы требуют
соответствующей проверки. Подробности предложены в
[утверждённой спецификации](superpowers/specs/2026-09-26-project-verification-evidence-design.md).
Выполнен [план реализации](superpowers/plans/2026-09-26-project-verification-evidence.md)
до локальной приёмки и установки. Оперативный статус финальной публикации:
[журнал доказательств](../qa/reports/evidence-2026-09-26.log).

26 сентября пользователь одобрил основу: отдельный регистратор реальных запусков,

Пройдено 80 тестов на Windows и Linux, реальные установки RU/EN/AZ и отрицательный контроль.

## Уточнения пользователя и выводы беседы

- Conductor используется глобально; личные правила каждого проекта уже ведутся отдельно.
  Не добавлять вторую систему проектных правил или дублирующий «паспорт» без доказанной нужды.
- Сохранять поддержку русского, английского и азербайджанского. Рабочие заметки этой
  сессии русские; они не заменяют три README и механизм выбора языка установки.
- «Общая память проверок» означает общую между агентами одного проекта, НЕ между проектами.
- Пользователь доволен текущим результатом. Систематическое невыполнение его просьб агентами
  в этой беседе не установлено. Нельзя выдавать такую гипотезу за диагноз проекта.
- Уточнения только при существенной неопределённости, проверка полноты, самопроверка,
  сохранение уроков и разделение ценностей/процесса уже присутствуют. Предлагать их как
  отсутствующие возможности было ошибкой анализа. До рекомендации сверять её с исходниками.
- Экономить лишние действия и объём отчётов, но не качество и необходимые доказательства.
- Пользователь ожидает обновления HANDOFF вместе с каждым завершённым изменением:
  выполненное, применимые проверки и оставшееся. Исторический аудит сохраняет свой срез;
  актуальные статусы находок относятся к текущей сводке, а не к переписанной истории.
- Документация не должна бесконтрольно разрастаться: поддерживать существующую краткую
  сводку и карту, не генерировать новую базу статей после каждой задачи.
- Ограничение 25 сентября «новых задач не начинать» отменено пользователем 26 сентября:
  начинаем память проверок, а Graphify обновляем после согласованного пакета изменений.
  Это не поручение автоматически реализовать весь исследовательский список улучшений.
- Обновлять Graphify штатными командами, не редактировать вручную сущности и связи графа.
- Защита удаления проектных правил важна как технический долг, но для преимущественно
  глобального использования не выбрана пользователем первым повседневным приоритетом.
- Случайно попавшую ранее стенограмму YouTube не считать пожеланиями пользователя.

## Точка восстановления текущей работы

### Рассмотренная автоматизация — не установлена

В установленном Graphify 0.9.67 `watch` автоматически обновляет кодовую часть;
изменения существующих документов требуют LLM-разбора, а `check-update` только сообщает
о необходимости обновления. Проверка `graphify hook status` показала отсутствие
post-commit/post-checkout hooks и merge driver в этом репозитории.

Для смыслового обновления документов найден готовый кандидат:
[GitHub Agentic Workflows](https://github.github.com/gh-aw/setup/creating-workflows/)
с примером Documentation Updater. Это агентный процесс с расходом ресурсов и настройкой
доступа, не гарантия правильности текста. Для пилота обсуждается ограничение существующими
файлами и небольшими предлагаемыми изменениями, без автоматического принятия.
[Mintlify](https://www.mintlify.com/docs/automations) тоже предлагает обновление документации
по изменениям кода. Пользователю понравился именно этот подход; это предпочтение для
дальнейшей оценки, не разрешение на подключение или оплату сервиса. По текущей официальной
документации автоматизации требуют Pro или Enterprise и расходуют кредиты при обновлении.
Пригодность для наших существующих Markdown-файлов без переноса документации ещё не проверена.
Ничего из этого не устанавливалось; пользователь просил пока исследовать варианты.
Проверка ссылок Lychee и обновления CI
через Dependabot обсуждались отдельно и не решают смысловую актуальность HANDOFF.

Уточнение о Graphify: в проверенных действующих файлах Conductor найден запуск навыка
по явному `/graphify` (`deploy/global-CLAUDE.md`) и обращение к карте перед исследованием
(`runtime/playbooks/investigating.md`), но не правило обновления после каждой задачи.
Установленная справка Graphify описывает отдельную команду `graphify agents install`,
добавляющую такое поведение в локальный AGENTS.md; соответствующего раздела в текущем
AGENTS.md нет. Это отличается от наличия команды обновления и от фонового наблюдения.
