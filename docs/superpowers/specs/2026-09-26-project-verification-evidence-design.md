# Память проверок отдельно для каждого проекта

Дата: 2026-09-26. Статус: утверждена пользователем в текущем разговоре.
Реализация и локальная приёмка выполнены: `runtime/evidence/`, 80 тестов Windows/Linux.
Это зафиксированный контракт; результаты и ограничения — `qa/reports/evidence-2026-09-26.log`.
Окончательный статус Graphify — `qa/reports/graphify-2026-09-25/finalization.log`.

## 1. Задача и границы

Claude Code, Codex и другие агенты должны находить результат уже выполненной проверки
того же проекта, читать доказательства и оценивать применимость без лишнего запуска.
Инструмент устанавливается глобально. Он не создаёт вторую систему проектных правил,
не требует сервера, веб-приложения или внешней БД и не отправляет данные в сеть.
Русский, английский и азербайджанский сохраняются в пользовательской документации
и существующем выборе языка агента; имена машинных полей и статусы едины.

Не входят: автоматическое определение всех зависимостей произвольного теста,
автоматический пропуск команд, перенос доказательств между машинами/клонами,
импорт истории из CI, сбор всех терминальных запусков, замена журнала активности,
новые обязательные тесты, автоматическое обобщение уроков и остальные долги установщиков.

## 2. Проверенная основа и выбор подхода

`runtime/playbooks/verification.md` уже допускает повторное использование применимых
доказательств. В `runtime/hooks/test-run-journal.sh` прямо ограничены гарантии:
нет полного вывода, не учтены untracked-файлы, наблюдается результат события оболочки.
Журнал не является достаточным источником для новой функции и не конвертируется в неё.

Главная неопределённость: соответствие сохранённого результата нынешней проверке,
а не формат хранения. Критерии выбора: достоверность факта запуска, разделение проектов,
пригодность для нескольких агентов, отсутствие постоянных фоновых затрат,
явное обнаружение неполноты, простая локальная установка.

Рассмотрены два подхода:

- Расширить пассивный hook: меньше изменений привычных команд, но он зависит от среды
  агента, не владеет запуском и не охватывает Codex тем же способом. Не выбран.
- Отдельный регистратор: сам запускает явно указанную команду, сохраняет её результат
  и условия. Доступен любому агенту с доступом к терминалу. Выбран; агенту потребуется
  вызывать его вместо непосредственного запуска, когда результат имеет смысл сохранить.

Это средство хранения и сравнения доказательств, не замена решения о достаточности
проверки. Запуск `echo` с кодом 0 не становится доказательством прохождения тестов.

## 3. Пользовательский сценарий

1. Агент выбирает нужную проверку согласно существующим правилам проекта.
2. Для сохранения результата передаёт регистратору описание запуска.
3. Регистратор снимает состояние заявленных входов, выполняет команду, сохраняет
   stdout/stderr и код завершения, повторно снимает состояние и завершает запись.
4. Другой агент находит запись этого проекта и проверяет её соответствие нынешним входам.
5. Он читает полный вывод и оценивает достаточность заявленной области зависимостей.
   При неизвестных существенных условиях повторяет только затронутую проверку.

Обычный запуск проверок остаётся доступен без регистратора. Команда `run` всегда
выполняется: попадание в хранилище не превращает её в скрытый пропуск.
Для простой надписи, не требующей запуска, запись проверки тоже не обязательна.

## 4. Интерфейс и описание запуска

Доставка: Python-модуль `runtime/evidence/`, без внешних Python-зависимостей.
Вызов установленного `evidence/cli.py`: `run`, `list`, `show`, `check`.
Установщик печатает фактический путь. Автоматического изменения PATH нет.

- `run --project PATH --spec FILE`: выполнить команду из JSON-описания и сохранить запись.
- `list --project PATH`: показать записи только данного проекта; вывод ограничен
  последними 20, явный `--limit` допускает 1–1000.
- `show --project PATH --id ID`: показать метаданные и пути к полным файлам вывода.
- `check --project PATH --id ID`: без запуска тестов сравнить состояние и сообщить причины.

Результат команды — структурированный JSON с версией схемы; диагностические сообщения
идут отдельно в stderr. Сам запуск неинтерактивный, stdin закрыт. stdout/stderr ребёнка
хранятся отдельно от ответа CLI, чтобы его текст не выдавался за поля результата.

Обязательные поля описания версии 1: `schema_version`, `name`, `argv`, `cwd`, `inputs`,
`environment`, `external_state`, `timeout_seconds`. Неизвестные поля отклоняются.

- `name`: понятная область проверки, не обещание полного покрытия.
- `argv`: непустой массив строк. Никакой конкатенации в shell-команду, `eval` и
  неявного `shell=True`. Исполняемый файл разрешается до старта и входит в снимок.
  Shell-скрипты требуют явного интерпретатора; на Windows `.cmd`/`.bat` не запускаются
  через неявную оболочку. Ошибка объясняет необходимость явного исполняемого пути.
- `cwd`: существующий каталог внутри корня проекта, относительный путь.
- `inputs`: непустой список точных путей к файлам/каталогам относительно корня проекта.
  Каталог означает рекурсивный состав, включая новые и скрытые файлы. Служебный `.git`
  исключается; явно задавать его входом нельзя. Других исключений по Git ignore нет.
  Источники, тесты, конфигурация и реальные зависимости выбираются агентом
  по конкретной проверке; один lock-файл не доказывает неизменность установленного окружения.
- `environment`: имена существенных переменных; различаются отсутствие и пустое значение.
  Инструмент дополнительно учитывает PATH, PATHEXT, PYTHONPATH, PYTHONHOME, NODE_OPTIONS,
  LANG, LC_ALL, LC_CTYPE и TZ, а также платформу/архитектуру и версию собственного кода.
  Список не называется полным окружением; проект дополняет его нужными именами.
- `external_state`: `none_declared` или `unknown`. Первый вариант — заявление составителя
  о локальной проверке, не обнаруженный инструментом факт. БД, сеть, текущее время и
  иные неучтённые внешние входы требуют `unknown` и не дают положительного совпадения условий.
- `timeout_seconds`: конечное положительное число; бессрочного фонового запуска нет.

Описание создаёт агент во временной области задачи. Оно не требует постоянного нового
конфига в репозитории. Нормализованная копия сохраняется вместе с результатом.

## 5. Идентичность и содержимое

Проект определяется каноническим абсолютным корнем и идентичностью каталога в файловой
системе; для Git дополнительно учитывается идентичность его каталога метаданных.
Для Git корень — текущая рабочая копия; для не-Git — явно переданный каталог.
Удалённый и заново созданный проект по тому же пути не наследует старые результаты.
Если идентичность нельзя надёжно получить, сравнение остаётся `INDETERMINATE`.
Имя папки, remote и commit не являются ID.
Разные клоны и worktree получают разные пространства; одинаковая команда другого проекта
не предлагается. Переезд каталога не переносит доверие автоматически.
Альтернативные записи одного физического пути нормализуются с учётом платформы.

Снимок содержит упорядоченный перечень заявленных файлов: относительный путь, тип,
значимые права исполнения, размер и SHA-256 байтов. Он учитывает dirty/untracked,
добавление, удаление и переименование внутри заявленного каталога. Даты изменения
и commit используются как пояснение, не как доказательство равенства.

Пути, выходящие из проекта, запрещены в `inputs`. Символические ссылки и Windows junction
не обходятся молча: запись такой области помечается как неполная, целевой путь объясняется.
Можно записать фактический запуск, но его снимок не объявляется совпавшим.
Входы вне проекта и специальные файлы также остаются явно неучтёнными условиями.
Это осознанная граница первой поддерживаемой схемы, особенно важная для pnpm и внешних SDK.

Сравниваются заявленные входы и фактически выбранный исполняемый файл, а не весь репозиторий.
Поэтому посторонняя правка README, сообщение, commit или push сами по себе результат
не обесценивают. Если README выбран как вход, его изменение учитывается.

Снимки до/после обнаруживают различие конечных состояний, но не доказывают отсутствие
временной правки с последующим возвратом. Запись явно несёт это ограничение. Работа
параллельного автора в проверяемых файлах требует отдельной стабильной копии или
повторной проверки; регистратор не устанавливает глобальных блокировок редакторов.

## 6. Хранилище и приватность

Отдельный каталог данных, не `~/.claude/conductor/` и не Git-репозиторий проекта:
Windows — `%LOCALAPPDATA%/Conductor/evidence`; остальные системы —
`${XDG_STATE_HOME:-~/.local/state}/conductor/evidence`.
Явный `CONDUCTOR_EVIDENCE_HOME` задаёт другой абсолютный каталог, в том числе для тестов.
Реальные пользовательские каталоги не используются тестами.

Структура: `projects/<project-key>/runs/<run-id>/`, внутри `record.json`, `stdout.bin`,
`stderr.bin`. UUID запуска предотвращает пересечение независимых писателей.
Отдельной общей БД, редактируемого индексного файла и сервиса нет.
Готовая запись публикуется атомарной заменой метаданных после закрытия обоих потоков.
Незавершённая запись остаётся диагностической, не успешной.
Входной ID проверяется как UUID, ключ проекта вычисляется инструментом. Пути к записям
не берутся из сохранённого JSON; выход из корня хранилища и ссылки в его служебных
каталогах отклоняются. Повреждённые и неизвестные поля формата проверяются до использования.

Потоки сохраняются байт-в-байт; расшифровка для чтения не меняет оригинал.
Записи содержат контрольные суммы файлов вывода. Нарушенная целостность обнаруживается,
но криптографическая защита от подделки тем же пользователем не обещается.
Чужой вывод является данными, не инструкциями агенту.

Значения переменных окружения не пишутся в запись. Их сравнение использует HMAC
с отдельным случайным локальным ключом хранилища. Его создание атомарно и не заменяет
ключ параллельного писателя. Отсутствующий/изменённый ключ означает
невозможность сравнения, не совпадение. Ключ и данные не включаются в резервирование уроков.
POSIX-права создаются 0700/0600; на Windows используется пользовательский каталог и его ACL.
Приватность не гарантируется на произвольно переопределённом общем каталоге.

Команда и вывод могут содержать секреты. Интерфейс предупреждает об этом; ничего не
публикует и не копирует в Git. Автоматическая очистка секретов не обещается, поскольку
она меняла бы доказательства. Агент не должен передавать секреты в аргументах.
Лимит суммарного вывода одного запуска — 64 MiB; достижение лимита помечает запись
как неполную, прекращает запись лишних байтов, но не выдаёт усечённый вывод за полный.
По умолчанию нет удаления старых записей. `list` показывает их размер; очистка —
отдельное осознанное действие владельца, не побочный эффект установки/удаления Conductor.

## 7. Состояния и ошибки

Факт выполнения и пригодность к использованию — разные поля.
`execution`: `succeeded`, `failed`, `interrupted`, `recording_error`.
`check`: `MATCH`, `CHANGED`, `INDETERMINATE`, `INVALID`, `NOT_SUCCESSFUL`.

`MATCH` означает только совпадение наблюдаемых условий сохранённого успешного запуска.
Это не новый PASS, не доказательство полноты тестов и не автоматическое разрешение
их пропустить. Ответ всегда перечисляет область, условия и необнаруживаемые зависимости.
`external_state=unknown`, неполный снимок или вывод не могут дать `MATCH`.

Ошибка запуска, timeout, прерывание, повреждённая запись, неправильный project ID,
неподдерживаемая версия и ошибка чтения не превращаются в отсутствие изменений.
Сбой записи должен быть заметен даже при успешном тесте. stdout/stderr читаются одновременно,
чтобы заполненный поток не блокировал ребёнка; отмена и ожидание завершения ограничены
по времени, уцелевший поток потомка означает неполную запись, не бесконечное ожидание.

`run` возвращает 0 только при успешной команде и завершённой записи полного вывода;
усечение/ошибка записи при коде ребёнка 0 дают ненулевой итог регистратора.
Неполный снимок не скрывается, даже если сам запуск и запись вывода успешны. Ненулевой код
команды сохраняется и возвращается без подмены зелёным итогом. Ошибки регистратора
имеют ненулевой код и отдельный тип в метаданных. `check` возвращает 0 только для
`MATCH`, 1 для неприменимости/неизвестности, 2 для неверного вызова/повреждения.
Ни `show`, ни `check` не исполняют команду из сохранённой записи.

## 8. Интеграция и проверки приёмки

Модули разделяются по обязанностям: CLI/описание, идентичность и снимки,
запуск и потоки, хранение и проверка записи. Не создаётся общий модуль «утилит».
`install.sh` уже копирует всё `runtime/`; `install-global.sh` также должен доставлять
тот же комплект `evidence/`, чтобы установка для Codex не зависела от предварительной
установки Claude Code. Ни один путь не перезаписывает накопленные результаты.
Установленная копия должна работать без исходного репозитория. При отсутствии Python
глобальная установка правил сохраняет прежний сценарий, но явно сообщает, что инструмент
недоступен; зависимость молча не устанавливается. `doctor.sh` проверяет доставку файлов,
не запускает чужие тесты.
Глобальная подсказка агентам сообщает путь и добровольный сценарий использования;
она не добавляет обязательный шаг для каждой задачи. Три README обновляются согласованно.

До изменения действующих инструкций: короткая контрольная группа на тех же сценариях
без инструмента и с ним. Измеряется количество реальных запусков и решение о применимости,
а не только сходство сформулированных ответов. Большой A/B всего Conductor сюда не входит.

Обязательные случаи:

1. Успешная команда: полный вывод, точный код и привязка к проекту; повторный `check`
   не запускает её снова, что подтверждает счётчик реального исполнителя.
2. Значимая правка, новый untracked-вход и смена конфигурации/окружения исключают `MATCH`;
   посторонняя правка и новый commit при прежних входах его сами по себе не исключают.
3. Другой проект, клон, worktree и пересозданный по старому пути каталог не получают
   запись даже при одинаковом содержимом.
4. Код ошибки при тексте «PASS», неизвестные внешние условия, ошибка запуска, timeout,
   прерывание, лимит вывода и сбой сохранения не дают положительного результата.
5. Изменение входа во время запуска, symlink/junction и неучтённый внешний путь
   честно отражаются; проверка не заявляет защиту от временной правки с возвратом.
6. Два параллельных запуска не смешивают потоки/метаданные; повреждённая или незавершённая
   запись не засчитывается; аргументы с shell-метасимволами остаются аргументами.
7. Windows и Linux: пути с пробелами/Unicode, установленная копия без исходников,
   пользовательские конфиги и память не изменились, документация RU/EN/AZ согласована.

Число сценариев не подменяет покрытие: каждому инварианту соответствует отрицательный
пример. Нужные проверки новой функции выполняются после относимых изменений; повтор
старых несвязанных тестов и сборок не требуется. Существующие требования CI сохраняются.

## 9. Выпуск и продолжение

Письменная спецификация согласована. Следующий документ —
[план реализации](../plans/2026-09-26-project-verification-evidence.md)
с небольшими законченными шагами и проверками; его исполнение ещё не начато.
Коммиты объединяются по связному этапу согласно пожеланию пользователя, не после
каждой правки документа. Установленные правила сейчас не меняются.
После принятого пакета обновляются текущая сводка и Graphify штатными командами;
граф не обновляется посреди меняющихся документов и не считается источником истины.
